### A.4 Target selection & grounding
- [x] Instruction parser/matcher: `visipilot/target_selection/instruction_parser.py::parse_instruction()` (rule-based clause splitting into FIND/TYPE/CLICK steps — chosen over an LLM parser per Instructions.md #3's pipeline-over-VLM default bias; there's no evidence yet that rule-based parsing is insufficient for Phase A's fixed instruction shapes) + `visipilot/target_selection/matcher.py::match_target()` (text + `label_of`-relation + structural-word scoring, resolving a target phrase against a `SemanticUIState`). **27 new unit tests pass** across `tests/test_instruction_parser.py` (7), `tests/test_matcher.py` (6), `tests/test_relations.py` (7), `tests/test_semantic_role.py` (8, counted under A.3 above). Also **4/4 real integration tests pass** (`tests/test_target_selection_integration.py`) running the full chain — real screenshot → real OWLv2 detector → real EasyOCR → `build_semantic_state()` → `parse_instruction()` → `match_target()` — against the controlled test page, with results scored against real DOM ground truth (eval-only, per the pixels-first rule: used only to check the matcher's output, never to produce it).
  - **A real bug was found and fixed during this integration testing, not hidden**: the test page's own distractor paragraph text literally contains the words "search box" (it describes the page's purpose in its own copy), and without a length-based penalty, naive token-overlap scoring ranked that paragraph *above* the real search input for the phrase "search box". Fixed with a general, non-page-specific heuristic in `matcher.py::_length_penalty()`: text longer than ~6 words is very unlikely to be a UI control's own label, regardless of token overlap. A regression test (`test_long_paragraph_incidentally_containing_phrase_words_loses_to_short_real_match`) locks this in.
  - **A second, honest finding — partially resolved in A.5**: for the phrase "search box" / "Search", the real search input's fused text ("Search:" — EasyOCR misread the input's "..." placeholder ellipsis as a colon) and the real Search button's text ("Search") score **exactly the same** — both tokenize to `{"search"}` once punctuation is stripped, so the matcher cannot distinguish "the input near the word Search" from "the button labeled Search" by text alone. This is a genuine limitation of the current signals (OWLv2's type field is unreliable, per A.2; OCR punctuation is not a robust signal), not a bug — and it's the *correct* system behavior per Instructions.md #7 (ambiguous candidates must be surfaced, never silently guessed): `match_target()` returns both as top candidates rather than picking one. **Update (A.5 milestone)**: an aspect-ratio-based geometric signal (`matcher.py::_aspect_ratio_bonus`, added alongside the action executor — real text inputs are much wider than tall, buttons are not) now correctly resolves the "search box" phrase (which contains a structural word) in favor of the real input. The bare "Search" phrase (the CLICK step's target, with no structural word to key off) remains genuinely tied — see A.5 for the real, honest end-to-end consequence of that.
- [x] Deterministic coordinate mapping module (`visipilot/grounding/coordinates.py`): screenshot px → viewport CSS px → page CSS px, accounting for DPR, zoom, and scroll offset. **20/20 unit tests pass** (`tests/test_coordinates.py`) covering DPR 1.0/1.25/1.5/2.0, zoom 1.0/1.25/1.5, scroll offset (viewport-clipped and full-page cases), combined DPR+zoom+scroll, round-trips, and error handling. **Additionally verified against a real browser**: `test_coordinate_mapping_matches_real_dom_ground_truth[1.0/1.5/2.0]` in `tests/test_capture_integration.py` confirms the mapping model matches live Playwright/Chrome DOM ground truth within 0.5px at three DPR values — this is real evidence the zoom/DPR modeling assumption documented in `ScreenshotMeta` holds for the DPR case; the zoom-factor part of the model is still unverified against a live browser (no zoom control wired up yet — see A.1 note) and remains an open item for Phase B.
- [x] Grounding: `bbox_to_viewport_click_point()` maps a `SCREENSHOT_PX` bbox to a viewport CSS click point; unit-tested (`test_bbox_to_viewport_click_point_center`, `test_bbox_wrong_space_raises`). Now exercisable end to end since target selection produces real bboxes — `test_target_selection_integration.py` uses `screenshot_point_to_viewport_css()` (the same underlying transform) to score matcher candidates against DOM ground truth, though a dedicated "grounding takes a matcher candidate and clicks it" wiring is still A.5's job, not yet built.

**Target selection latency**: `build_semantic_state()` ~0.46 ms, `parse_instruction()` ~0.04 ms, `match_target()` ~0.11 ms/call — all pure Python, negligible next to the detector/OCR inference cost measured in A.2. Confirms these stages won't meaningfully affect the ≤5 s/instruction Phase A budget.

### A.5 Action & verification
- [x] Action executor: `visipilot/action/executor.py` (`click_element`, `type_into_element`, `resolve_single_candidate`) + `visipilot/action/runner.py` (`run_steps`, sequencing FIND→TYPE→CLICK through the matcher and executor for a parsed instruction). Trusted input events only (`page.mouse.click`, `page.keyboard.type` — never a JS-injected click or a direct value assignment). `resolve_single_candidate` enforces Instructions.md #7: it raises `NoConfidentTargetError` below a minimum confidence (0.3) and `AmbiguousTargetError` when the top candidates are tied within an epsilon (0.05) — the runner stops rather than guessing in either case, and a single pass with no retries is a deliberate scope choice (bounded by construction; real retry/re-perception policy belongs to A.6/Phase C, not half-built here ahead of that design work). **10/10 unit tests pass** (`tests/test_executor.py`, mocked Playwright page) + **5/5 unit tests pass** (`tests/test_runner.py`, including a test that a genuinely tied CLICK step halts without clicking). **4/4 real integration tests pass** (`tests/test_action_integration.py`): a real trusted click on the real "Subscribe" button lands inside its true DOM bbox; a real FIND+TYPE resolves and types "Python" into the real search input (the aspect-ratio fix from A.4 is what makes this resolve unambiguously); and — reported honestly, not hidden — running the **exact vertical-slice instruction** for real against the real page succeeds on FIND and TYPE but halts at CLICK with `FAILED_AMBIGUOUS`, reproducing the tied "Search:" vs "Search" ambiguity documented in A.4. - [x] Evaluation-mode-only DOM check: `visipilot/eval/dom_verification.py::dom_text_present()` — isolated in `visipilot/eval/`, whose package docstring already states it's never imported by runtime code; this file adds no exception. **A.4's tie was partially closed as part of the A.5 milestone**: the FIND step's "search box" vs "Search" ambiguity was resolved with an aspect-ratio-based geometric signal (real UI text inputs are much wider than tall, buttons are not). The CLICK step's bare-"Search" ambiguity remained open at that point, since neither structural words nor aspect ratio apply to a phrase with no structural word.

**Update (A.6 milestone) — the CLICK-step ambiguity is now resolved too, with evidence, not a hack.** Before implementing anything, the ambiguity was analyzed empirically: what general visual signal, if any, could distinguish "Search:" (input) from "Search" (button) when text alone can't? The real screenshot was sampled directly (this project's own real pixel data, not assumed) at four real elements' bboxes:

| Element | Real fill (avg RGB) | Saturation | Distance from white |
|---|---|---|---|
| search input | (255,255,255) white | 0.000 | ~0 |
| newsletter input | (251,251,251) near-white | 0.000 | ~4 |
| Search button | (87,125,255) blue | 0.659 | ~293 |
| Subscribe button | (188,188,189) gray | 0.004 | ~116 |

A first hypothesis ("high color saturation = button") was tried and **rejected**: the page's own gray Subscribe button has saturation 0.004, statistically indistinguishable from the white inputs' 0.000 — it would not have generalized. **Distance-from-pure-white**, tested second, cleanly separates all four real elements regardless of whether the button happens to be brand-colored or a neutral gray: real text-entry controls are overwhelmingly styled white/near-white (the default browser style, kept for legibility of typed text); real buttons — colored or neutral — are reliably some visible distance from that. This matches a genuinely common, near-universal web design convention, not something tuned to this one page — though it is *not* universal, and that limitation is stated up front (see below).

Implemented as `visipilot/target_selection/visual_signals.py::fill_distance_from_white()` (samples the real screenshot image directly — allowed by Instructions.md #2's actual pixels-first rule, which permits target selection to use screenshot pixels and only forbids DOM/AX access; the README's stricter "never over raw pixels" paraphrase of this boundary was inaccurate and has been corrected) and wired into `matcher.py::_fill_bonus()`, **gated off whenever a structural word is present** in the phrase specifically so it cannot re-introduce the tie `_aspect_ratio_bonus` already fixed for "search box"-style phrases (verified by hand-computing both cases before wiring it in, then confirmed by test). **5/5 new unit tests pass** (`tests/test_visual_signals.py`, synthetic images with exact real-world colors) + **4 new matcher tests pass** (`tests/test_matcher.py`): the bare-"Search" tie now resolves to the real button; the structural-word case is unaffected; and — the critical safety check — **`test_genuine_tie_between_two_identically_styled_buttons_is_preserved` confirms two truly indistinguishable candidates still score an exact tie**, so `resolve_single_candidate()` still correctly raises `AmbiguousTargetError` rather than guessing. The no-blind-clicking rule is unchanged; only the set of cases that are genuinely ambiguous got smaller, backed by real measurement.

**Stated limitation, not fixed here**: this breaks for "ghost"/outline buttons with a white or transparent fill, and for dark-mode pages where inputs may not be styled white. Flagged as a Phase B item, to be measured against real dark-mode/varied-styling test pages once they exist rather than guessed at now.

**Real-world consequence**: running the exact vertical-slice instruction against the real page now succeeds end to end — FIND, TYPE, and CLICK all resolve and execute correctly (see A.6 below for the traced, verified run). `tests/test_action_integration.py::test_full_vertical_slice_instruction_succeeds_end_to_end` replaces the earlier test that only proved the safe-halt behavior.

**Resource measurement** (full chain: screenshot → OWLv2 detect → EasyOCR read → build_semantic_state → parse_instruction → FIND+TYPE via the real action executor → screenshot → pixels-first verify): **2789.7 ms total**, well under the ≤5 s/instruction Phase A budget; find+type action latency **15.4 ms**; verification (OCR re-run) **483.7 ms**; **peak VRAM 1708.6 MB** — identical to A.2's detector+OCR baseline, confirming the action/verification stages add no additional VRAM (verification reuses the already-loaded OCR model, and Playwright's mouse/keyboard APIs are CPU-only).

### A.7 Trace record schema (as implemented)
Adapted from the original sketch to the types actually built in this project — one record per whole-instruction run (matching what `run_steps()` already returns), and OCR output reuses `list[UIElement]` (`source=OCR`) rather than a separate `OCRResult` type, so there's no second schema to keep in sync:
```python
class TraceRecord(BaseModel):
    run_id: str
    instruction: str
    screenshot_hash: str
    detected_elements: list[UIElement]
    ocr_elements: list[UIElement]
    fused_elements: list[UIElement]
    action_records: list[ActionRecord]
    verification: VerificationResult | None = None
    stage_timings_ms: dict[str, float] = Field(default_factory=dict)
    model_versions: dict[str, str] = Field(default_factory=dict)
    runtime_info: RuntimeInfo
    failure_reason: str | None = None
```

### A.8 Vertical-slice evaluation harness
- [x] `visipilot/eval/vertical_slice.py` — a CLI (`python -m visipilot.eval.vertical_slice`) that loops `visipilot.tracing.pipeline.run_instruction()` N times against a live page, reusing one browser and one loaded detector/OCR pair across the whole batch (fresh `page.goto()` per run to reset in-page JS state — a normal navigation, not a DOM manipulation) and scores each run against DOM ground truth (`visipilot/eval/dom_ground_truth.py` — eval-only, exactly the module the pixels-first rule already carves out for this purpose; the pipeline it calls remains pixels-first throughout). ## Phase B — Robustness

**Goal:** the slice generalizes beyond one page layout.

### B.1 Controlled page suite and evaluation infrastructure

### B.3 Real bugs found and fixed (all with regression tests, all motivated by this investigation, none by "make a page pass")
- [x] **Fusion first-match bug** (`visipilot/perception/fusion.py::fuse()`): when an OCR text box overlapped *multiple* detector boxes above the absorption threshold, the OLD code assigned it to whichever detector box came first in iteration order — not the best match. Found on `search_small_icons.html`: OWLv2 produced both a precise box tightly matching the real input and a spurious, oversized box spanning an unrelated toolbar plus the search row; both fully contained the "Search" OCR text (overlap ratio 1.0 each — overlap ratio alone can't distinguish a tight fit from a loose one), and the spurious box won purely by list position. **Fixed in two steps, both evidence-driven**: (1) assign each OCR box to the detector box with the *highest* overlap ratio, not the first one reaching threshold; (2) on an exact ratio tie, prefer the *smaller-area* (tighter) detector box. **2 new regression tests pass** (`test_fuse_ocr_text_goes_to_best_overlap_not_first_match`, `test_fuse_full_containment_tie_prefers_smaller_detector_box`), all 6 pre-existing fusion tests still pass unchanged.
- [x] **Verification text-fragmentation bug** (`visipilot/action/verification.py::verify_text_present()`): on `search_bootstrap.html`, the DOM confirmed `#results` correctly contained "Results for: Python" and OCR correctly read every word of it — but EasyOCR split it into two separate regions ("Results for:" and "Python") instead of one, and the old verification only checked individual OCR regions, so it reported failure on a run that actually succeeded completely. **Fixed** by grouping OCR regions into visual lines (by overlapping vertical center — a plain top/bottom sort can reverse same-line fragments with different detected text heights, which is exactly what happened here: centers matched at ~349px, y-tops differed at 341 vs 335) and checking each line's joined text, never the whole page joined into one string (an earlier version of the fix did that and was caught by its own test producing a false positive from unrelated, distant page text — see the regression test for it). **3 new regression tests pass**, all 4 pre-existing verification tests still pass unchanged.

Not a bug fix — new, tested capability needed to make the below-the-fold page a meaningful test at all (a viewport-only capture would never see the target, which would just test "the system can't see what it can't see," not scroll-awareness).

### B.5 Investigating and closing the "confidently wrong click" (icon-button) finding

**Investigated before any code changed, per this milestone's explicit rule.** Re-ran `build_semantic_state()` against the real `search_small_icons.html` screenshot and inspected the actual computed relations: the real button (`det-10`, bbox almost exactly matching DOM ground truth) already had a `nearby` relation to the real input (`det-9`, which absorbed the misread "Search..." placeholder) — option (b) from the earlier note, using the existing `nearby` relation, was directly testable. The input had **8 other `nearby` neighbors** too (toolbar icons, a distractor paragraph — 39 `nearby` pairs total on this one page), so a naive "any nearby textless interactable" rule would have been noisy; the button was reliably the *closest* one by edge gap.

**Two false starts, both caught by testing against real pages before trusting the fix — not assumed correct:**
1. First version picked the closest neighbor by **bbox-center distance**. On the real page, a large spurious detector box that heavily *overlapped* the input had a center closer to the input's center than the true (small, non-overlapping) button — purely because the overlapping box's own size distorted its center position. Fixed by excluding neighbors that overlap the matched element (reusing the same "spurious duplicate detection" insight fusion.py's B.3 fix already established) and ranking survivors by **edge-to-edge gap** instead of center distance.
2. Even after that fix, re-running the **full 6-page suite** (not just the one page being fixed) found a **new regression**: `search_bootstrap.html`, which had no icon-button ambiguity at all, started failing. A large (375×96), non-overlapping, textless detector box happened to sit within the `nearby` distance threshold of the real Search button there and was wrongly treated as an "adjacent icon," redirecting the click to it — a wrong click that **did not exist before this feature**. Real icon-only controls are compact; fixed by also requiring both dimensions of a candidate neighbor to be ≤48px (`_NEIGHBOR_MAX_DIMENSION_PX` in `visipilot/target_selection/matcher.py`).

**Design of the fix, once validated**: rather than guess which of two candidates (a text-matched element and its closest small, non-overlapping, textless interactable neighbor) the user means — a genuine, currently-unresolvable ambiguity given OWLv2's unreliable type field — `match_target()` now **ties their scores**, so `resolve_single_candidate()`'s existing, already-tested `AmbiguousTargetError` path fires instead of confidently picking the (arbitrary) higher scorer. This is deliberately *not* an attempt to correctly identify the right target; it's a conversion of "confidently wrong" into "safely refuses," exactly matching this milestone's explicit instruction that a safe refusal is preferable to a confident wrong action. Gated off for phrases containing a structural word ("box"/"field"/"input"), so it cannot re-introduce the tie the A.5/A.6 aspect-ratio/fill-color fixes already removed for those phrases — verified directly (`match_target("the search box")` still resolves uniquely) before and after each iteration of the fix.

**4 new regression tests pass** (`tests/test_matcher.py`): the real tie-creation case, the structural-phrase gate, a neighbor-with-text exclusion (a labeled button beside the input must not be redirected to), and the exact overlapping-spurious-box false start reproduced and locked in. **19/19 matcher tests total pass**, all pre-existing tests unchanged.

### B.6 Investigating whether textless icons can be *labeled*, not just safely refused (no new model)

**Explicit follow-up to B.5**: B.5 converted the icon-button failure from a confident wrong click into a safe refusal — it deliberately did not attempt to make the icon findable. This milestone investigated whether the *existing* pipeline (already-loaded OWLv2 detector, EasyOCR, semantic relations, geometry) can supply a reliable general signal for what a textless icon control means, before considering any new model.

**Signal 1 — OCR: confirmed empty, as expected.** `search_small_icons.html`'s button renders a Unicode magnifying-glass glyph (`&#128269;`) as element content, not an `<img>`. Direct measurement: 0 of 13 real OCR regions on the page overlap or lie near the button's true bbox — EasyOCR does not read the emoji glyph as text at all. This was checked empirically, not assumed from the earlier "no text" finding. OCR genuinely has nothing to contribute for this class of control.

**Signal 2 — OWLv2 type field, with an expanded icon-descriptive query vocabulary: tested and found unreliable, confirming rather than overturning the existing A.2 finding.** Added icon-descriptive queries (`"a small icon button"`, `"a toolbar icon button"`, tested initially with a page-specific `"a magnifying glass search icon"` query too) alongside the existing two, re-typing matched boxes as `ElementType.ICON` — this needed no new model or code change to test, since OWLv2 is already loaded and zero-shot (arbitrary text queries are free). Measured directly against real screenshots for all 6 Phase B pages:
- On `search_small_icons.html` itself, one `ICON`-typed detection was a genuinely tight fit (17×17 vs the true 16×16 button, overlap ratio 1.0, confidence 0.379) — the best case, and on its own looks promising.
- But run across the other 5 pages, the same `ICON` query vocabulary also labeled: the *entire* search-input-plus-button row on `search_basic.html` as `ICON` (bbox 451×41px, overlap 0.98 with the real *text*-labeled button, confidence only 0.082 — indistinguishable by confidence from the tight true-positive case above); a large, loosely-fitting box on `search_bootstrap.html` (overlap 1.0 but bbox nearly 5× the true button's area); and the whole search row on `search_dark_mode.html` (overlap 1.0, confidence 0.076). None of these are real icon-only controls — `search_basic.html`'s button has a visible "Search" text label. **Confidence does not separate the true positive from the false positives** (0.379 vs 0.082/0.076/0.243 — no usable threshold exists in this data). This is the same underlying weakness the A.2 finding already documented (OWLv2 is a natural-image zero-shot detector, not UI-trained) — expanding the query vocabulary changes *what gets a box*, not the *reliability* of the label. Using `type == ICON` to gate or auto-resolve target selection would risk introducing a new confident-wrong-action failure mode (mislabeling a real, text-bearing button as an anonymous icon), which the milestone's explicit instruction rules out.

**Signal 3 — geometry/relations: already exploited by B.5, has no further semantic content to give.** The `nearby` relation and size/overlap gating (B.5) already extract everything geometry alone can offer: *that* a compact, textless, interactable control sits beside a matched element. Geometry has no channel for *what the icon depicts* (a magnifying glass vs. a settings gear vs. a trash can) — that requires actually interpreting the icon's visual content, which none of the currently-loaded models are built to do zero-shot with any reliability (OCR reads text glyphs, not pictographic ones; OWLv2 localizes objects/regions, its text-label matching is the unreliable part, not something a differently-phrased query fixes).

**Conclusion: the existing pipeline cannot reliably label textless icon controls.** All three available signal families were tested empirically, not assumed insufficient: OCR contributes nothing (confirmed empty), the detector's open-vocabulary type/caption signal is measurably unreliable even with a better-targeted query set (confirmed via a 6-page comparison, not just the one page motivating this investigation), and geometry/relations have no semantic channel to exploit further. This satisfies the "only evaluate a new model if evidence shows the existing pipeline cannot reliably label/resolve" condition.

### B.7 The bounded Florence-2-base benchmark (run, not just planned) — result: not currently usable

**Goal, per B.6's own recommendation**: measure whether Florence-2-base's region-captioning task actually produces captions that *semantically* match instruction phrases for real textless icon controls, not just whether it locates one, using B.5's existing candidate-narrowing predicate (compact + textless + interactable) to decide what to caption — exactly matching what a future runtime integration would feed it.

**Test fixtures built**: three new minimal icon-only pages (`testpages/icon_settings.html`, `icon_menu.html`, `icon_close.html`, each a single 18×18px icon-only control with a distinct real meaning — gear/settings, hamburger/menu, X/close), used alongside the existing `search_small_icons.html`, so the benchmark covers 4 distinct icon meanings, not just the one that originally motivated this investigation (an explicit ask, to check the caption's *content*, not just presence). New eval module: `visipilot/eval/icon_caption_bench.py`, reusing `_is_icon_candidate()` (identical criteria to B.5's `_closest_textless_interactable_neighbor` gating: interactable, textless, ≤48px per dimension) so the benchmark tests captioning exactly the candidates a real integration would feed it, never a hand-picked crop.

**Finding 1 — Florence-2-base's official HF remote code does not load against `transformers==5.17.0`, the project's already-verified, currency-checked pin, without unofficial monkeypatches to Microsoft's own code.** Three independent, successive incompatibilities were found and diagnosed in order, each only surfacing after patching the previous one:
1. `Florence2LanguageConfig.__init__` accesses `self.forced_bos_token_id` before `super().__init__()` sets it — `transformers` 5.x's stricter `PretrainedConfig.__getattribute__` (via its new "heterogeneity" config integration) raises `AttributeError` instead of returning a default, where older transformers versions silently tolerated this.
2. `Florence2Processor.__init__` accesses `tokenizer.additional_special_tokens` as a plain attribute — removed/renamed in the currently-installed tokenizer API.
3. `PreTrainedModel.__init__`'s new attention-implementation auto-dispatch logic (`_check_and_adjust_attn_implementation`) accesses `self._supports_sdpa`, an attribute Florence-2's model class never sets, because its remote code predates that dispatch mechanism.
4. Even past all three, `.generate()`'s default caching path fails with `TypeError: 'EncoderDecoderCache' object is not subscriptable` — Florence-2's remote `prepare_inputs_for_generation` still assumes the old tuple-based `past_key_values` format `transformers` 5.x replaced.

A web search corroborated this is not an artifact of this one machine's setup: **huggingface/transformers#36886** documents Florence-2 breaking starting `transformers` 4.50.0 (released well before the 5.x line this project already uses), unresolved by Microsoft as of this writing — a real, external, already-known-and-unfixed upstream incompatibility, not a local misconfiguration.

**Finding 2 — even when coerced past all four blockers (`attn_implementation="eager"`, `use_cache=False`, plus monkeypatches 1–2), the checkpoint's own language-model weights fail to load.** `transformers`' own load report flagged `language_model.model.decoder.embed_tokens.weight`, `language_model.lm_head.weight`, and `language_model.model.encoder.embed_tokens.weight` as `MISSING` — "newly initialized because missing from the checkpoint" — meaning the weight-key names in Florence-2's checkpoint no longer match what the currently-installed `transformers`' loading machinery expects. **Confirmed empirically, not assumed from the load report alone**: captioning a solid-blue 64×64 test swatch produced fully incoherent, image-unrelated text (`'iscAbstract480 dressedeve repe mafiaoft556 Archangel deputies...'` — verified against the raw generated token IDs, not a decoding artifact) — exactly the signature of randomly-reinitialized embedding/output-projection weights, not a real (if imperfect) caption.

**Finding 3 — a separate, unrelated detector-recall gap surfaced while building the benchmark**: with the production 2-query set (`"a rectangular text input box"`, `"a button"`), OWLv2 detected **zero** boxes at all on `icon_settings.html` and `icon_menu.html` (both real 18×18px controls near the viewport's right edge) — not a false type, no box at all. `search_small_icons.html` and `icon_close.html` were localized correctly (detector bbox overlap ≥0.5 with DOM ground truth). This means candidate narrowing itself has real, page-dependent recall gaps upstream of any captioning step — a separate, honestly-reported finding, not investigated further this milestone (out of scope for a Florence-2 benchmark specifically) but relevant to any future work in this area.

**Bounded benchmark result, run for real** (`python -m visipilot.eval.icon_caption_bench`, report at `out/icon_caption_bench_report.json`, gitignored, reproducible): Florence-2-base loaded (with the documented monkeypatches) and ran without raising, so `florence_load_error` is `None` in the report — but this must not be read as "it works": of the 2 pages where a candidate was actually localized and captioned (search, close), **0/2 captions semantically matched their expected keyword set** (both were incoherent word-salad, per Finding 2). **Peak VRAM with Florence-2-base (fp16) loaded alongside the existing OWLv2+EasyOCR baseline: 2508.8 MB** (vs. 1708.6 MB baseline — Florence-2-base itself added ~800 MB, consistent with its small, ~0.23B-parameter size) — comfortably within the ≤6 GB budget, but this number describes a model whose output is currently unusable, not a validated capability.

**License/dependency note**: Florence-2-base's weights remain MIT-licensed (unaffected by the compatibility issue), but loading its custom modeling code required two additional dependencies, `einops` (MIT) and `timm` (Apache-2.0) — both small, permissively licensed, and installed **only** for this bounded evaluation, deliberately **not** added to `requirements.txt`, since Florence-2 is not being integrated into the runtime pipeline this milestone.

**Conclusion: Florence-2-base is not currently worth integrating.** This is not a licensing, VRAM, or latency problem (all of those look favorable on paper, as B.6 found) — it is a real, reproducible, externally-corroborated upstream compatibility failure between Florence-2's unmaintained custom remote code and the project's already-verified, current `transformers` pin, compounding into silently-wrong (randomly-initialized) weights when forced to load anyway. Forcing it to work would require either (a) pinning `transformers` to a version older than 4.50.0 (released well before the currently-verified 5.17.0), which conflicts directly with Instructions.md #2's currency rule and would need to be re-verified against this project's Blackwell/cu128 CUDA stack from scratch, or (b) maintaining a patched fork of Microsoft's own remote code indefinitely — both exactly the kind of "bespoke build" burden Instructions.md #2 says to avoid when a reasonable alternative exists. B.5's safe-refusal behavior for textless icon controls remains the correct, currently-shipped behavior; it was not weakened or second-guessed by this investigation.

**Exit criteria for this milestone**: the bounded experiment was run, not just planned — accuracy (0/2 semantic match, with the other 2/4 pages blocked upstream by a separate detector-recall gap), false positives (0 usable captions to be falsely positive about — none were coherent), latency (793.8 ms and 477.9 ms per caption, single-crop, fp16, RTX 5060), VRAM (2508.8 MB peak with Florence-2-base loaded), Windows/RTX 5060 compatibility (loading required 3 independent monkeypatches plus 2 new dependencies, and even then produces unusable output — a clear **fail** on compatibility), and license (MIT, confirmed, not the blocker) were all measured, not estimated. **Met.**

### B.8 Investigating the OWLv2 recall gap (before evaluating another VLM)

**Root cause, established before any adjustment was tried**: `UIDetector`'s production query set (`"a rectangular text input box"`, `"a button"`) does propose a box at the true location of the `icon_settings.html`/`icon_menu.html` icons (overlap 0.85–0.94 with DOM ground truth), so this is **not** the detector being blind to these regions — it's a **confidence-calibration gap**. Raw scores at those true-location boxes are 0.079 (settings) and 0.082 (menu), both below the production `score_threshold=0.1`, so they never reach the semantic-state candidate list at all (confirmed via a `score_threshold=0.01` probe in `visipilot/eval/icon_recall_experiment.py`). This is consistent with, and further evidence for, the already-documented A.2 finding: OWLv2 is a natural-image zero-shot detector, and flat, monochrome, sub-20px vector UI glyphs (a gear, a hamburger icon) are further outside its training distribution than a colored rectangular button shape (`search_small_icons.html`'s button, which has a solid blue fill and was recalled correctly at conf 0.39 in earlier investigation) or a clean X-glyph on a light background (`icon_close.html`, recalled at conf ≥0.1 too).

**Three evidence-based adjustments were tested, measuring recall (does the true icon get a compact candidate with ≥0.5 bbox overlap) against false positives (compact, textless, interactable candidates appearing on pages that have no real small-icon target at all — `search_basic.html`, `search_bootstrap.html`, `search_dark_mode.html`, `search_duplicate.html`, `search_scroll.html`) — real command, real numbers, `python -m visipilot.eval.icon_recall_experiment`, report at `out/icon_recall_experiment_report.json`:**

| Configuration | Recall (of 4 icon targets) | Total false-positive compact candidates (5 non-icon pages) |
|---|---|---|
| Production baseline (2 queries, threshold 0.1) | 2/4 | 0 |
| + icon-descriptive queries, threshold unchanged (0.1) | 3/4 | 4 new (basic, bootstrap each gain 1) |
| + icon-descriptive queries, threshold lowered to 0.05 | 4/4 | 27 (spread across bootstrap, dark_mode, duplicate, scroll, basic) |
| Threshold lowered to 0.05 alone, no vocabulary change | 4/4 | 19 (same pages, somewhat fewer) |

Every configuration that recovers full recall does so by **generating false-positive compact-interactable candidates on pages that previously had zero** — precisely the failure class B.5 already found and fixed once (a spurious compact candidate on `search_bootstrap.html` wrongly redirected a click). Lowering the threshold alone recovers full recall with fewer added false positives than adding queries does, but the false-positive count (19, spread across 4 of the 5 previously-clean pages) is still a real, generalized increase in the "spurious `nearby` tie" risk surface B.5's safety mechanism depends on staying rare — not a page-specific quirk being fixed, but a global change with a measured, non-trivial cost across the whole page suite.

**A fourth adjustment — image resolution — was also tested and found ineffective**, ruling out "the icon is too small for OWLv2's patch grid to resolve" as the mechanism: 2× upscaling the full screenshot before detection moved confidence at the true location from 0.079→0.086 (settings) and 0.082→0.089 (menu) — a ~7–9% relative change, nowhere near closing the gap to the 0.1 threshold, let alone to a safely separable confidence level. This means the low confidence is a genuine zero-shot semantic-recognition ceiling (OWLv2 doesn't strongly associate these flat glyph shapes with "a button"/"a rectangular input" regardless of pixel detail available), not a resolution artifact.

**Decision: none of these adjustments were adopted.** Per this milestone's explicit instruction not to blindly tune thresholds or weaken safety for a page-specific win, and because every recall-improving change tested here trades away exactly the "false positives near zero on pages with no icon" property the B.5 safety design relies on, `UIDetector`'s defaults remain unchanged (`DEFAULT_QUERIES`, `score_threshold=0.1`) — locked in by a new regression test (`test_production_detector_defaults_unchanged_by_this_investigation`) specifically so a future change here is a deliberate, evidence-weighed decision, not an accidental regression discovered late.

**Conclusion: OWLv2 cannot provide sufficiently reliable icon candidates for this class of control, even after reasonable evidence-based adjustment** — confirming rather than contradicting B.6/B.7's conclusion that the existing pipeline (detector included) has a real, now precisely-characterized ceiling for flat, textless icon glyphs. This satisfies the condition for evaluating whether a VLM should be benchmarked **independently of OWLv2 candidate generation** (i.e., not gated behind OWLv2 successfully proposing the box first, since that's exactly the step now shown to fail for ~50% of the icon types tested).

**Next-step feasibility note, not a benchmark**: a lightweight Moondream2 (`vikhyatk/moondream2`, Apache 2.0) loadability sanity check was attempted this milestone, given Florence-2's B.7 compatibility surprise — it did not complete (a multi-GB weight download did not finish in a reasonable time on this sandboxed connection, consistent with the slow/stalled-download behavior already noted for large model pulls in Phase 0's GPU smoke-test setup) and was stopped rather than left running unbounded. This is **inconclusive, not a finding** — Moondream2's actual Windows/RTX 5060 compatibility remains unverified and is real future work, not assumed either way.

**Resource note**: this investigation reused the already-loaded OWLv2 detector and EasyOCR at their existing measured resource footprint (no new model loaded for the recall/threshold/query experiments); the 2× upscale probe processes one extra image resize per page tested (CPU-only, PIL, negligible cost, not separately measured as it does not change the production pipeline).

### B.9 Moondream2 benchmarked independently of OWLv2 — result: also not currently viable

**Goal, per B.8's recommendation**: since OWLv2 cannot reliably propose candidates for this control class, evaluate Moondream2 (`vikhyatk/moondream2`, Apache 2.0) **decoupled from OWLv2 entirely** — crops for this benchmark are taken directly from DOM ground truth (eval-only, exactly the sanctioned use of `visipilot/eval/dom_ground_truth.py`: deciding where to crop for scoring, never producing a runtime target), so the question tested is purely "can Moondream2 understand what a textless icon depicts", independent of whether OWLv2 can find it. New eval module: `visipilot/eval/moondream_bench.py`, run for real against all 4 icon pages (search, settings, menu, close).

**Loadability, checked first, per this milestone's explicit instruction, before any accuracy benchmarking**: Moondream2 (revision `2025-06-21`, the revision documented in the model's own usage instructions at investigation time) **does not load cleanly against this project's already-verified `transformers==5.17.0`** either, though the failure is shallower and different in kind from Florence-2's (B.7). `from_pretrained`'s device-dispatch path (`transformers/integrations/accelerate.py`) directly accesses `model.all_tied_weights_keys` with no `getattr` fallback; Moondream2's custom `HfMoondream` remote-code class never sets this attribute (its remote code predates this `transformers` 5.x internal expectation), raising `AttributeError: 'HfMoondream' object has no attribute 'all_tied_weights_keys'`. **A single one-line monkeypatch** (`PreTrainedModel.all_tied_weights_keys = {}` as a class-level default) was enough to get past it — a much shallower compatibility gap than Florence-2's four-layer cascade, and no extra dependencies were needed (unlike Florence-2's `einops`/`timm`).

**But loading without raising is not the same as loading correctly — confirmed decisively, not assumed.** With the patch applied, weight loading completed (592/592 tensors, no `MISSING` report this time — unlike Florence-2, the checkpoint's own weight keys did match). Despite that, real captioning against all 4 real icon-page crops (not a synthetic test image) produced **the same class of incoherent, repetitive garbage across every page** — e.g. `'1PhotPhotPhotPhotKeKeKe...'`, long runs of a single repeated token (`'...Tem??Tem??Tem??Tem??...'`), completely unrelated to any of the four distinct icon images. **0/4 captions semantically matched their expected keyword set.** This strongly suggests the class-attribute patch, while sufficient to avoid a crash, bypassed a real weight-tying step `all_tied_weights_keys` was meant to drive (tying token-embedding and output-projection weights is exactly what that attribute name describes) — i.e. the patch prevents a crash but not silent incorrectness, the same category of problem as Florence-2's missing/reinitialized weights, via a different mechanism.

**Latency makes this decisive on its own, independent of the coherence question**: per-caption latency measured **51.8–70.5 seconds** across the 4 real pages (fp16, RTX 5060, `length="short"`) — two orders of magnitude beyond Instructions.md #3's "well under a few seconds per step" requirement, and far beyond even Florence-2's already-unusable-but-comparatively-fast 478–794 ms. Even with a hypothetically correct model, this latency alone would disqualify Moondream2 for this project's interactive-agent budget without further investigation into why it's this slow (e.g. whether the patched load path disabled a fast code path `all_tied_weights_keys` was also involved in).

**Resource measurement**: peak VRAM **4435.2 MB** for Moondream2 alone (fp16) — stacked on top of the existing OWLv2+EasyOCR baseline (1708.6 MB), this would total **~6.1 GB**, at or over the project's ≤6 GB ceiling. Model load time: 25.4 s (cold, cache warm from a prior partial download this session). License remains Apache 2.0, confirmed, not the blocker.

**Conclusion: Moondream2 is also not currently viable, for reasons structurally similar to Florence-2's (B.7) despite a shallower loading fix.** Both of the two most promising candidates identified in B.6's desk comparison have now been shown, empirically, to load in this project's currency-verified `transformers` environment only via unofficial monkeypatches, and to produce unusable output even once loaded — a pattern (not a coincidence specific to one model) strongly suggesting this project's `transformers==5.17.0` pin, while correct and necessary for the already-shipped OWLv2/EasyOCR pipeline, is simply ahead of what several actively-used custom-remote-code HF vision-language models have been updated to support. Forcing either to work correctly would require real, non-trivial reverse-engineering of what each monkeypatch actually broke (weight tying, most likely) — squarely the "bespoke build" burden Instructions.md #2 says to avoid, now demonstrated twice, not assumed.

**Exit criteria for this milestone**: loadability (fail without a patch, borderline-functional-at-best with one), dependency compatibility (no new dependencies needed, unlike Florence-2), VRAM (4435.2 MB, would push the combined pipeline to the budget ceiling), latency (51.8–70.5 s/caption — decisively disqualifying on its own), license (Apache 2.0, confirmed), and maintenance/currentness (the pinned `2025-06-21` revision does not handle current `transformers`; whether a newer, unpinned revision does remains unverified — see below) were all measured for real, not estimated. **Met.**

**Explicitly not investigated further this milestone, and why**: whether the default/unpinned `main` revision of Moondream2 (potentially newer than `2025-06-21`) fixes either the loading gap or the output-coherence problem was not checked — the `2025-06-21` revision is what the model's own current usage documentation names, and with latency alone already disqualifying at 10-14x the project's total per-instruction budget, chasing a possible coherence fix would not change the outcome. Not investigated as not warranted by the evidence in hand, not overlooked.

**Resource measurement across the suite**: peak VRAM per page ranged **1708–3813 MB**; peak RAM **2382 MB** suite-wide — both comfortably within the ≤6 GB / ≤12 GB budgets, but the range itself is a real finding: `full_page=True` capture on the scroll page (a ~2500px-tall image vs. an 800px viewport) **more than doubled peak VRAM** (3812.6 MB vs. ~1709 MB on every other page) and OCR latency (~1.8–2.2 s vs. ~0.3–0.5 s) — a real, measured cost of full-page capture that matters for any future work on scroll-aware perception, not something to assume is free.

### B.10 Stale-screenshot detection, occlusion, and the zoom/DPR sweep

Closes B.4's three remaining open items — chosen over pursuing a third small-VLM candidate per this milestone's explicit instruction, and because Instructions.md #7's stale-screenshot rule is a binding requirement, not a Phase B robustness nice-to-have.

**Stale-screenshot detection (Instructions.md #7).** New `visipilot/capture/screenshot.py::screenshot_has_changed()`: a cheap re-screenshot-and-hash-compare against a reference `Screenshot`. Verified empirically before trusting it as a signal (not assumed): repeated real captures of an unchanged static page produce an *identical* hash every time in this project's headless-Chrome setup (no cursor-blink/antialiasing noise), so an exact mismatch reliably means real content changed. Wired into `visipilot/action/runner.py::run_steps()`, called before every CLICK/TYPE action (the only steps that act on coordinates); on a detected change, the step fails with the new `ActionOutcome.FAILED_STALE_SCREENSHOT` rather than clicking — implemented as **detect-and-refuse**, not a full automatic re-perception-and-retry loop, which is real, separate multi-step/retry-policy design work that belongs with Phase C, not bolted on here ahead of that design (the same scoping call A.5 already made for CLICK/TYPE's own retry policy).

**A real bug found and fixed via real-page testing, not assumed away**: the first version compared every step against the *original* `state.screenshot`. Running the real vertical-slice instruction (FIND → TYPE → CLICK) against this immediately failed at CLICK — because the TYPE step's own echoed input text ("Python" appearing in the search box) legitimately changes the page's rendered pixels, so comparing CLICK against the pre-typing screenshot always looked "stale" even with nothing external happening. **Fixed** by rolling the comparison reference forward after every successful action (re-screenshotting once, cheaply, after each TYPE/CLICK success) so each step is only compared against the state the *previous* step actually left behind — this correctly catches only genuinely external changes between one action and the next. Re-verified: the full real vertical-slice instruction succeeds end to end again (`tests/test_action_integration.py`, `tests/test_tracing.py`).

New test page `testpages/search_dynamic.html`: a banner appears 200ms after load, shifting the search row down (a real late-loading-ad/consent-banner pattern). 200ms was chosen deliberately, not arbitrarily — an earlier version used 600ms (comfortably under this project's *cold-cache* ~1.7s perception latency, the number available at design time), but running the full page suite repeatedly surfaced a real race: with a *warm* model cache, this project's fastest observed screenshot+detect+OCR latency is only ~450–500ms, so a 600ms banner sometimes landed *after* the first action's staleness check had already passed, producing genuinely nondeterministic suite results (one run even got a click through before the banner appeared, only caught downstream by verification — a real, honestly-observed edge case in the "detect-then-act" design: the check narrows the vulnerable window from the whole perception pipeline down to the gap between the last check and the actual mouse event, but that gap is not literally zero). Lowering the delay to 200ms (below even the fastest observed case) makes the page-suite demonstration deterministic across cold/warm runs; the dedicated unit tests below use explicit `page.wait_for_timeout()` control regardless of the page's own delay, so they're unaffected either way.

**4 new regression tests** (`tests/test_stale_screenshot.py`, real Playwright, no mocks): no false positive on a static page; real detection of the late banner; `run_steps` refuses a CLICK when the page changed since perception; a normal multi-step run (FIND→TYPE→CLICK) still succeeds without the runner's own TYPE action being mistaken for staleness. **A second real bug was found and fixed while writing these**: the CLICK-refusal test's synthetic fixture originally included both the search input and button as candidates, relying on `match_target`'s real fill-color tie-breaker (`_fill_bonus`) to disambiguate — this passed reliably in isolation but failed intermittently when run deep inside the full 162-test suite (reproduced twice, not a one-off). Simplified the fixture to a single unambiguous candidate (the test doesn't need FIND/TYPE's competing element at all) rather than chase the exact system-load-dependent interaction further — this removed the dependency entirely without weakening what the test actually checks, and made the full-suite run deterministic again (confirmed clean on repeated re-runs).

**Real, full-pipeline evidence** (`search_dynamic.html` added to `visipilot/eval/page_suite.py`, real 5-run evaluation): **5/5 runs correctly refuse via `failed_stale_screenshot`** at the TYPE step, using the real detector/OCR pipeline end to end — not a mocked demonstration. Task-success rate is 0/5, exactly as expected: this page is deliberately constructed so the safe-refusal path is the only correct outcome, the same "0% task success is the right answer" pattern already established for `search_duplicate.html`/`search_dark_mode.html`.

**Occlusion.** New test page `testpages/search_occluded.html`: a small sibling `<span>` badge ("NEW") absolutely positioned over the search button's top-right corner — a real hazard pattern (a notification badge/tooltip that isn't a pointer-events-none decoration) verified via `document.elementFromPoint()` to actually intercept clicks at that corner, while the button's own center remains unaffected. **Result: 5/5 success, 100% click accuracy** — the existing pipeline handles this specific occlusion pattern correctly with no code changes needed; the detector still localizes the button correctly and the grounded click point (bbox center) lands clear of the badge. No generalizable bug found here, so none was manufactured — a real, honestly-reported negative result, added to the suite as a permanent regression check.

### C.1 Bounded re-perception retry + the clarification path

**Investigated the existing architecture before adding anything**, per this milestone's explicit instruction. Two facts shaped the design:

1. `run_steps()` already took an injected `stale_check` callable with a real default — so re-perception and clarification are injected the same way (`reperceive`, `clarifier`) rather than inventing a second extension mechanism. The runner still imports no perception model code; the closure that owns the detector/OCR lives in `tracing/pipeline.py`, where they were already loaded.
2. Ambiguity and staleness need *opposite* treatment. Re-perceiving an unchanged page returns the same tied candidates, so retrying ambiguity is a guaranteed-useless loop — it goes to a clarifier instead. Staleness is the opposite: the page genuinely changed, so a fresh perception pass is exactly what's needed. **Only staleness is retried.**

**Retry flow.** On a detected stale screenshot the runner now re-runs the real perception chain (capture → detect → OCR → build), re-resolves the step's target against the *fresh* state, and retries — instead of Phase B's immediate refusal. Re-resolution matters: re-perception rebuilds every element id from scratch, so a TYPE step's previously-FIND-focused candidate no longer refers to anything on the page and is re-resolved from the phrase that produced it (locked in by `test_type_step_reresolves_its_target_against_freshly_perceived_state`). Grounding metadata is likewise read from the *current* state each attempt, never a value captured before a re-perception.

**Limits are explicit and finite** (`RetryPolicy` in `visipilot/action/runner.py`): `max_attempts_per_step=3` (one attempt plus the two retries the Phase A pass criteria already specified) and `max_reperceptions_per_run=3`, a separate whole-run budget so a long instruction can't multiply per-step allowances into an arbitrarily long run. Exhausting either is a new, terminal `ActionOutcome.FAILED_RETRY_EXHAUSTED`, distinct from the staleness that triggered the retry. A page that *never* settles terminates deterministically — proven, not asserted, by `test_permanently_changing_page_stops_at_per_step_attempt_limit` (always-stale stub → exactly 2 re-perceptions, then a bounded stop, never a click).

**Every retry is observable.** `ActionRecord` is now one record *per attempt* carrying `attempt`, `reperceived`, and `clarification_used`, so a retried step shows its failed attempt *and* its successful one rather than collapsing into a single after-the-fact outcome. `TraceRecord.retry_summary` aggregates them — and is **derived from the records** in `pipeline.py` rather than counted separately in the runner, so the summary and the records it summarizes cannot drift apart. Each re-perception is separately timed into `stage_timings_ms` as `reperception_N_ms` and logged (`stage=reperception`). Verified to survive into the on-disk artifact evaluation actually reads (`test_retry_summary_and_records_round_trip_through_the_trace_file`).

**Clarification path** (`visipilot/action/clarification.py`): a `ClarificationRequest` (action, phrase, tied candidates) goes to an injected `Clarifier`, with `cli_clarifier` as the "even if simple, e.g. CLI prompt" mechanism the roadmap asks for. **The default is no clarifier, i.e. exactly the pre-Phase-C safe refusal** — so this cannot silently weaken the no-blind-clicking rule, and declining (empty input, non-numeric, out-of-range, EOF/non-interactive stdin) all fail closed. Per Instructions.md #6, candidate text is page-derived and therefore untrusted: the prompt prints it behind an explicit `page text:` delimiter, quoted, and only a numeric choice is accepted back, so page content can describe a candidate but never steer the selection (`test_prompt_labels_page_derived_text_as_page_content` uses a literal "ignore previous instructions" payload).

### C.3 Ordinal/reference resolution ("open the second result")

**Built on the existing pieces, not alongside them**, per this milestone's explicit instruction — inspected the parser, matcher, executor, and clarification flow before writing anything:

- `InstructionStep` (instruction_parser.py) gained one field, `ordinal: int | None` — 1-based, or `-1` for "last" (Python-style negative indexing, reused deliberately rather than inventing a second sentinel convention). A new `_extract_ordinal()` strips a leading ordinal word ("first"/"second".../"1st"/"2nd".../"last") off the already-captured target phrase, so "the second search button" becomes phrase="search button", ordinal=2 — the ordinal word itself never becomes part of the text-matching phrase, since no real element is ever literally labeled "second". "open" was added as a `_CLICK_RE` synonym for "click", since the roadmap's own canonical example uses it.
- `resolve_single_candidate` (executor.py) gained an optional `ordinal` parameter, defaulting to `None` — **zero behavior change for every existing caller.** When given, it picks the `ordinal`-th of the candidates already tied for the top score, by reading order (bbox center, top-to-bottom then left-to-right) — never past the tied group into lower-scored, less-relevant matches, and never by DOM/HTML source order, which pixels-first perception never sees at runtime (Instructions.md #2). An out-of-range ordinal raises a new `OrdinalOutOfRangeError` → `ActionOutcome.FAILED_ORDINAL_OUT_OF_RANGE`, a distinct terminal outcome from `FAILED_AMBIGUOUS`: the tie isn't the problem (an ordinal is exactly the disambiguating information a tie needs), the requested position just doesn't exist, and picking the closest existing one instead would be exactly the guess Instructions.md #7 forbids.
- `run_steps` (runner.py) threads `step.ordinal` through FIND/CLICK resolution and tracks `focused_ordinal` alongside `focused_phrase` so a TYPE step re-resolves correctly by *both* after a Phase C.1 re-perception (an ordinal-qualified FIND target must survive a retry the same way a plain one already did). An in-range ordinal is resolved directly and never reaches the injected `clarifier` — it doesn't need clarification, it already has a safe, deterministic answer.
- `match_target`'s pool size at the runner's call sites was widened from the default `top_k=3` to `_ORDINAL_CANDIDATE_POOL=10`, so a duplicate-element page with more than 3 copies doesn't silently truncate the pool an ordinal indexes into. Harmless for non-ordinal resolution, verified by the unchanged existing-test results — `resolve_single_candidate` only ever inspects the top-scoring tied group regardless of how many lower-scored candidates are also in the list.

**Two new real test pages**, plus reuse of the existing one:
- `testpages/search_results_list.html` — 3 results, each with an identically-labeled "Result" button (the real reason an ordinal is needed at all: text alone cannot distinguish them), DOM order matching visual order.

### C.4 Fixing the `search_dynamic.html` timing race, then verification-failure retry

**Timing-race root cause, found by measuring rather than assuming (a third time, on the same test page — see B.10's original 600ms→200ms retune for the first two).** The C.3 milestone's report hypothesized the machine had simply gotten faster than the 200ms banner delay assumed. That was half right and led to the wrong fix if taken at face value: direct measurement showed real screenshot+detect+OCR+build latency is still **1131–2371ms** (min observed 1131ms) — comfortably *slower* than 200ms, not faster. The actual mechanism was different and more specific: `launch_page()`'s navigation plus the time to capture the very first ("before") screenshot was measured **independently** at **285–461ms** on its own — and that, not full perception latency, is what the 200ms delay needed to be compared against. Since capturing that first screenshot already takes longer than 200ms, the banner had *already appeared* by the time any test's "before" screenshot was taken, so the before/after comparison the page exists to exercise never actually observed a change — both screenshots showed the post-banner state, and every test that depended on detecting the difference silently stopped testing anything.

**Fix**: raised the banner delay to **700ms** — verified, not assumed, against both boundaries this time: `700ms > 461ms` (the worst-case navigation-to-first-screenshot time, measured directly, so the "before" screenshot reliably predates the banner) and `700ms < 1131ms` (the fastest observed full perception pass, so the banner has reliably already appeared by the time a CLICK/TYPE step's staleness check runs). Confirmed the banner is *not* visible at first capture across 5 repeated real captures, then confirmed the full previously-flaky test set (`test_stale_screenshot.py` + `test_tracing.py`) passes cleanly across 3 repeated runs, and the full suite passes cleanly across 2 repeated full runs (223/223 both times) — the same "repeat it and check" discipline that caught the original C.3 finding, applied one more time before trusting the fix. No C.3 ordinal behavior was touched; `tests/test_ordinal_resolution.py`'s 11 tests were re-run and pass unchanged.

### C.5 One re-perception cycle on verification failure

**The other explicit, binding pass-criterion C.1 didn't yet implement**: the original Phase A pass criteria (implementation-plan.md, "Failure/retry limits") specify "maximum 1 full re-perception cycle per step *on verification failure*" — C.1 only implemented re-perception for *pre-action* staleness (a stale screenshot detected before a CLICK/TYPE executes). Verification runs once, at the very end of a whole instruction, and until this milestone a failed check just failed the run outright.

**Design decision, made explicit rather than defaulted into**: on a failed verification check, the retry **re-perceives and re-checks — it does not re-execute the action.** The click/type already happened and reported `SUCCESS`; if the click's effect just hasn't rendered yet (a debounced search, an async results panel, a fade-in — all real, common UI patterns), giving it more wall-clock time via a fresh perception pass and checking again is the correct fix. Re-clicking on a verification failure was considered and rejected: it risks a real, worse failure mode than a slow render — a second, unintended action (e.g. double-submitting a form, double-incrementing a counter) — which is exactly the class of consequence Instructions.md #7's bounded-retry rule exists to prevent. "Re-perception cycle" in the original wording maps naturally to "look at the page again," not "redo what was already done."

Implemented as `visipilot/tracing/pipeline.py::_verify_with_retry()`: checks a fresh screenshot; on failure, if a re-perception budget remains (shared with C.1's `RetryPolicy.max_reperceptions_per_run` — staleness retries and the verification retry draw from the *same* overall ceiling, not two independent ones), triggers exactly one more `_reperceive()` call and re-checks against *its* fresh screenshot. `VerificationResult` gained a `retried: bool` field so a passed-after-retry result is distinguishable from a passed-on-first-try one in the trace, and `RetrySummary.reperceptions` (already documented as "derived from the records so it can never drift") now also folds in `verification.retried` so the aggregate stays accurate rather than silently under-counting this new retry source.

**New real test page**: `testpages/search_slow_render.html` — the click's handler fires and reports success immediately (identical to every other test page), but the visible results text is deliberately written **800ms** later via `setTimeout`, simulating a debounced/async render. The delay was chosen the same way B.10/C.4's banner delay was: measured, not assumed. Real timing: the *first* verification check (screenshot + OCR) takes 465–554ms and reliably finds nothing (the 800ms delay hasn't elapsed); the retry's `_reperceive()` call (a full screenshot+detect+OCR+build pass) plus its own fresh check together add real wall-clock time comfortably past 800ms, and the retried check reliably finds the text (confirmed across 5 repeated real runs, 5/5). A `data-click-count` attribute on the real button, incremented by its real click handler, gives a direct DOM-level proof (not just an inference from internal outcome codes) that the retry never issues a second real click — confirmed at exactly `1` after a full, successful, retried run.

**Real measured before/after** (`tests/test_tracing.py`, real Playwright, real OWLv2 + EasyOCR):

| Configuration | `search_slow_render.html` result |
|---|---|
| `enable_retry=False` (no verification retry) | **Fails every run** (3/3) — `verification failed: 'Results for: Python' not found...`, `retried=False` |
| `enable_retry=True` (this milestone) | **Succeeds every run** (5/5) — `verification.retried=True`, `retry_summary.reperceptions=1`, the click itself still shows `attempt=1` (never re-executed) |

**Full 9-page suite** (`python -m visipilot.eval.page_suite --runs-per-page 5`, `search_slow_render.html` added): **5/5 success, 100% click accuracy** on the new page; all 8 existing pages unchanged (`basic`/`bootstrap_style`/`dynamic_content`/`occluded_button` 5/5; `small_icon_button`/`dark_mode`/`duplicate_search_boxes`/`scroll_below_fold` correctly refusing exactly as before). Suite peak VRAM **3812.6 MB**, peak RAM **2452.2 MB** — unchanged from the pre-C.5 suite, confirming the verification retry reuses the already-loaded models like every other retry path in this project. Real per-retry cost, measured from 5 real traces: **469–554 ms (mean 502 ms)**, consistent with C.1's original re-perception measurement (512–599 ms) — the same underlying operation, same cost profile.

**Tests**: 4 new real-browser tests in `tests/test_tracing.py` (fails-without/succeeds-with the retry in one test; the real DOM click-count proof; a permanently-failing phrase still terminates after exactly one retry, never loops; a normally-passing page pays no retry cost). ### D.2 EasyOCR optimization experiment — negative result, none adopted

**Treated D.1's finding as the target, per this milestone's explicit instruction**: EasyOCR (37.8% of total traced time) was investigated, not the detector (18.4%). Evaluated the three most realistic avenues for EasyOCR's existing GPU inference path — INT8 dynamic quantization, FP16/half-precision inference, and ONNX Runtime's CUDA execution provider — before changing any production code, via a new `visipilot/eval/ocr_optimization_experiment.py`. **All three were tested for real and found non-viable; `visipilot/perception/ocr.py` is unchanged.**

**1. INT8 dynamic quantization: a confirmed no-op, not just theoretically unhelpful.** EasyOCR's own `Reader(quantize=...)` flag only calls `torch.quantization.quantize_dynamic` on its `device == 'cpu'` code path (`easyocr/detection.py::get_detector`, `easyocr/recognition.py::get_recognizer`); the `gpu=True` branch this project always uses ignores the flag entirely. Verified programmatically, not just by reading the source: two `Reader` instances built with `quantize=True` and `quantize=False` on `gpu=True` produce identical model types, identical `float32` parameter dtypes, and identical state-dict keys.

**2. FP16 (`torch.autocast`): crashes the detector outright, and makes the recognizer measurably *slower*, not faster, despite preserving accuracy.** EasyOCR's CRAFT detector post-processing (`easyocr/craft_utils.py::getDetBoxes_core`) calls `cv2.threshold()` directly on the raw FP16 model output; OpenCV does not support FP16 arrays there, producing a hard, real crash (`cv2.error: ... Unsupported format`) on every one of 3 representative real pages tested. The separate recognizer network (CRNN) does not hit that code path and runs correctly under FP16 — text output and confidence scores matched FP32 within noise (max confidence delta <0.02, identical text recognized on every region across all 3 pages, 5 repeated runs each) — but was measurably **slower**, not faster: **-45.1%, -23.2%, -4.3%** across the three pages (mean -24.2%), consistent with a small model/small per-call batch size where `autocast`'s own dtype-casting overhead outweighs any FP16 tensor-core benefit, and with D.1's isolated `match_target()` finding that this pipeline's bottlenecks are not raw-compute-bound in the way half precision is built to help with.

**3. ONNX Runtime's CUDA execution provider: installed but non-functional in this environment.** `onnxruntime-gpu` 1.30.0 lists `CUDAExecutionProvider` as "available" (`onnxruntime.get_available_providers()`), but a real session requesting only that provider silently falls back to `CPUExecutionProvider` — confirmed via `session.get_providers()` after construction, the same "verify the specific path actually works, don't trust that it's listed" discipline this project has applied to every prior model/library evaluation (B.7, B.9). Root-caused precisely from onnxruntime's own diagnostic output, not guessed: `Error loading ...onnxruntime_providers_cuda.dll which depends on cublasLt64_13.dll which is missing` / `Require cuDNN 9.* and CUDA 13.*` — this version of onnxruntime-gpu requires **CUDA 13.x**, while this project's verified, working PyTorch stack is pinned to **cu128 (CUDA 12.8)**. (An earlier version of this check tested for CUDA-12-era DLL names via `ctypes.CDLL` and found them "present" — that was misleading: PyTorch's own import adds its bundled DLL directory to the process search path, so the lookup was finding PyTorch's private CUDA-12.8 copies, not confirming onnxruntime's actual CUDA-13 requirement was satisfied. Corrected to check the exact dependency onnxruntime's own error names, `cublasLt64_13.dll`, confirmed genuinely absent.) Making this path work would mean installing a full, separate CUDA 13 Toolkit + cuDNN 9 system-wide, alongside (not replacing) the existing, already-verified cu128 stack every other model in this project depends on — exactly the invasive, speculative infrastructure investment this milestone's instructions rule out, especially with finding (2) already suggesting the bottleneck isn't raw compute throughput a different execution engine would help with anyway.

**Decision: none of the three adopted.** Per this milestone's explicit instruction to reject any optimization that improves latency while materially degrading accuracy/safety, and given none of the three even offers a latency improvement to weigh against that risk (a no-op, a crash, and a measured slowdown), there is nothing to integrate. `visipilot/perception/ocr.py` is unchanged; no fallback path is needed because no change was made in the first place.

**Compatibility verification (Windows + RTX 5060 Blackwell), as required before considering any production change**: performed for all three avenues before any accuracy/latency comparison was run — this is precisely what surfaced findings (1) and (3) as blocking, before any further investment.

**Real evaluation, repeated real-browser runs across 3 representative pages** (`search_basic.html`, `search_bootstrap.html`, and `search_scroll.html` — the D.1-identified full-page-capture outlier — 5 runs each): confirms findings (1)–(3) are not single-page artifacts. Full 9-page Phase B suite re-run after the investigation (no production code changed, so this is a consistency check, not a before/after): all safe-refusal pages (`small_icon_button`, `dark_mode`, `duplicate_search_boxes`, `scroll_below_fold`) behave exactly as previously documented; `basic`/`bootstrap_style`/`occluded_button`/`slow_render_results` remain 5/5. **One real, honestly-reported observation, unrelated to this milestone's changes**: `dynamic_content` showed 3/5 success (was consistently 5/5 in C.4/C.5/D.1) across two independent suite runs during this investigation. Traced to its root cause, not dismissed: in the 2 failing runs, the CLICK step succeeded (attempt 1, no staleness detected) and landed at coordinates computed from the *pre-banner* layout, and the subsequent verification-retry (C.5) correctly re-perceived and re-checked but still failed — because the click itself never actually landed on the real button in the post-banner layout, so no amount of re-checking can find text that a missed click never caused to appear. This is the already-documented "narrow gap" limitation from B.10/C.1 ("the check narrows the vulnerable window... but that gap is not literally zero") manifesting at a higher rate this session than when first observed — confirmed via zero uncommitted changes to any runtime code this investigation touches (`git status` shows only the two new eval/test files), so it is pre-existing session-to-session timing variance, not a regression introduced by this milestone. Safety held throughout: every one of these runs correctly reported `failure_reason` set, never a false success. Out of scope for D.2 to fix; noted for whoever next revisits C.1/C.5's timing margins.

**Resource measurement**: peak VRAM **3221.7 MB** during the experiment itself (lower than D.1's 3812.6 MB full-suite figure since this experiment doesn't exercise the `full_page=True` scroll page's OCR path the same way — expected, not a discrepancy). No lasting resource change: production code is unchanged, so the shipped pipeline's VRAM/RAM footprint is identical to D.1's baseline.

**Dependencies**: `onnxruntime-gpu`, `onnx`, and `onnxscript` were installed locally only for this experiment (needed to export a real, minimal model and construct a real `InferenceSession` — not assumed compatible from documentation alone), **not added to `requirements.txt`**, since nothing using them was integrated — the same precedent set by B.7/B.9's Florence-2/Moondream2 experiments (`einops`/`timm` installed locally, never added to the pinned requirements).

**Tests**: 4 new (`tests/test_ocr_optimization_experiment.py`) — lock in all three findings so a future EasyOCR/onnxruntime-gpu upgrade or environment change (e.g. a system CUDA 13 Toolkit installed for an unrelated reason) is caught rather than silently invalidating this milestone's documented conclusion; a passing test here is a deliberate signal to re-read this section, not something to ignore. The ONNX-related test skips gracefully if `onnxruntime` isn't importable in a given environment. Full suite: **232/232 passes**, confirmed clean.

**Exit criteria**: every one of the requested checks — Windows/Blackwell compatibility verification, OCR latency, end-to-end latency, OCR accuracy, downstream target accuracy, safe-refusal behavior, VRAM/RAM, startup/model-load cost — was measured for real against a real baseline (D.1's own numbers) across repeated real-browser runs, and the negative result is documented with the same rigor an adopted optimization would have received. **Met.**

## Vertical-slice pass criteria (Phase A)

These numbers are intentionally modest and explained, not arbitrary:

- **Minimum successful runs:** 20 consecutive runs of the exact instruction on the base test page, ≥18/20 (90%) succeed end-to-end (correct element found, correct action taken, verification passes). 20 runs is enough to distinguish "reliably works" from "got lucky once" without requiring a large dataset before any pipeline code exists; 90% leaves room for legitimate transient flakiness (e.g. a slow page load) while still requiring the core loop to be dependable.
- **Page variants at this phase:** 1 (the base page) for the pass gate itself; Phase B is where variant count scales up. Testing only 1 page here keeps Phase A focused on proving the mechanism works before proving it generalizes.
- **Click/grounding accuracy:** click point must land inside the target element's true bounding box (from DOM ground truth, eval-only) in ≥95% of successful runs — a click just outside a 40×40px button is a real failure mode this must catch.
- **Task success rate:** ≥90% (see above), defined as: correct element clicked, "Python" typed correctly, Search clicked, and verification confirms the expected state change.
- **Maximum acceptable latency:** ≤5 seconds per full instruction (screenshot → perception → grounding → action → verification) on this hardware. Chosen as a generous but real ceiling for an interactive local agent — tightened in Phase D once a baseline exists; not tightened prematurely before real numbers exist.
- **Peak VRAM:** ≤6 GB, per the project's hard constraint — measured via `nvidia-smi` or `torch.cuda.max_memory_allocated()` during the run, not estimated.
- **Peak RAM:** ≤12 GB for the Python process (leaving headroom on a 16 GB machine already running a browser and OS) — a soft ceiling to be tightened if real numbers come in much lower.
- **Failure/retry limits:** maximum 2 retries per action step, maximum 1 full re-perception cycle per step on verification failure; a task that still hasn't succeeded after that returns a structured failure, never loops indefinitely.
